Architecture

How Mobile Manager watches the foreground app, decides, and enforces — and how the code is split so that every decision can be unit tested without a device.

Layers and modules

The project follows MVVM with three layers mapped onto three Gradle modules:

  • Domain (:core:domain) — pure Kotlin/JVM. It owns the models ({{Rule}}, {{Profile}}, {{StrictSession}}, {{ZoneDetectorFile}}…), the decision logic ({{RuleEngine}}, {{ProfileResolver}}, {{ScheduleEvaluator}}, {{ZoneMatcher}}, {{LockPolicy}}, {{DashboardCalculator}}) and the repository interfaces ({{ProfileRepository}}, {{ZoneUsageRepository}}, {{LockRepository}}…). Time always comes from {{TimeProvider}}, so midnight, daylight saving changes and weekdays are covered by tests.
  • Data (:core:data) — Room and DataStore implementations of the repositories.
  • App (:app) — Android: the accessibility service, foreground service, receivers, Compose screens and ViewModels. ViewModels expose StateFlows; each screen is split into a XxxScreen that wires the ViewModel and stateless content.

Enforcement chain

  1. {{MonitorAccessibilityService}} receives TYPE_WINDOW_STATE_CHANGED and TYPE_WINDOW_CONTENT_CHANGED events. It only reads package names for the foreground decision; content events are ignored immediately except for apps that have zone detectors and for protected settings screens.
  2. {{ForegroundTracker}} keeps the current app. Only windows that are real activities change it: launcher panels (Google Discover, listed in {{HomePanels}}), widgets, popups, the notification shade and keyboards are ignored.
  3. {{EnforcementCoordinator.evaluate}} combines the {{SystemWhitelistProvider}} (launcher, dialer, clock, settings, keyboards, Mobile Manager itself), the usage read by {{UsageStatsReader}}, the active layers from {{ProfileResolver}} and the {{RuleEngine}}. Profiles, global rules and the manual activation are kept in memory with stateIn, so an evaluation never reads the database.
  4. A {{Decision.Blocked}} shows {{BlockActivity}} in its own task (excluded from recents). The screen is always shown again (apps that chain two screens at launch would otherwise cover it) but the event log deduplicates a block of the same app within 2 s.
  5. A {{Decision.Allowed}} is re-evaluated after min(remaining time, 30 s) ({{EnforcementPolicy.nextCheckDelay}}) while the app stays in front; re-evaluations stop when the screen turns off and resume when it turns on.

Important

No GLOBAL_ACTION_HOME is sent before the block screen: the action is asynchronous and the home screen ended up above the block screen. {{BlockActivity}} itself returns to the home screen (button or back).

Usage time

Time used today comes from UsageStatsManager.queryEvents() (ACTIVITY_RESUMED / ACTIVITY_PAUSED, almost real time), read from midnight minus 6 hours and cut at midnight by {{UsageCalculator}}. Nothing is stored for this: the computation survives a restart of the service and stays consistent with Android’s Digital Wellbeing. {{UsageCalculator.usageByPackage}} follows the global foreground timeline: opening an app closes the previous one, and screen off, shutdown and startup events close everything, so an app left open during a crash is not counted until now.

Zone runtime

{{ZoneEnforcer}} handles events of apps that have detectors. It captures only what it needs (see Zones and detectors), asks {{EnforcementCoordinator.evaluateZone}} for a decision that includes the time already spent in the zone, then either counts time ({{ZoneUsageRecorder}}), or leaves the zone ({{ZoneExitPlanner}}) and masks its entry button ({{EntryPointMask}}).

Threads and scopes

  • The accessibility service runs its coroutines on Dispatchers.Main.immediate; accessibility tree captures and decisions run on Dispatchers.Default, because every node read is a round trip to the observed app.
  • Long-lived state shared by the service and the UI uses the application scope ({{ApplicationScope}}).
  • Receivers started by the system ({{BootReceiver}}) obtain their dependencies through {{SessionEntryPoint}} instead of field injection.

Dependency injection

Hilt everywhere: {{MobileManagerApp}} is the Hilt application and also provides the WorkManager configuration (Configuration.Provider) for {{DailyUsageWorker}}. Repositories are bound in {{DataBindingsModule}}, the database, DAOs, DataStore and {{TimeProvider}} are provided by {{DataProvidersModule}}, and app-level objects by {{AppModule}}.

Startup

At startup {{MobileManagerApp}} seeds the defaults once (each guarded by a DataStore flag): the disabled default profiles ({{SeedDefaultProfiles}}), the blocked Reels and Shorts zones ({{SeedDefaultZoneRules}}) and the TikTok block ({{SeedDefaultAppBlocks}}), and takes daily usage snapshots ({{DailyUsageSnapshotter}}).

Privacy by construction

  • No network permission is used for any feature; there is no account and no telemetry.
  • allowBackup=false and the data extraction rules exclude everything: nothing goes to a cloud backup.
  • Zone detection reads view identifiers, short labels of navigation tabs and selection states — never message or post text. Captures of the diagnostic mode stay in memory.
