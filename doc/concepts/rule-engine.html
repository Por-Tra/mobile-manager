Rule engine and profiles

Every decision — “may this app (or this zone of it) be used right now?” — is taken by the pure RuleEngine from layers of rules resolved by ProfileResolver. Both live in :core:domain and are covered by unit tests.

Rule model

A Rule is a Target plus a RuleAction.

TargetSpecificityMeaning
Target.AllAppslowestEvery app not covered by a more specific rule.
Target.AppmiddleOne package, for example com.instagram.android.
Target.ZonehighestA zone of a package, for example Instagram reels. Only applies when the zone is detected on screen.
ActionMeaning
RuleAction.BlockForbidden.
RuleAction.LimitAllowed up to a daily duration (a quota when the target is a zone).
RuleAction.AllowExplicit exception: stops the evaluation of lower layers.

A forbidden time range is simply a profile with Rule(AllApps, Block) plus Allow exceptions.

Schedules

A Schedule is a set of weekdays plus a local start and end time:

  • end <= start crosses midnight (the days are the days of the start);
  • start == end means 24 hours;
  • the start is included, the end excluded.

ScheduleEvaluator handles daylight saving time (a non-existent local time is shifted forward; a repeated hour is covered twice) and chains contiguous ranges to compute when a period ends. Being active and having an end are different questions: ScheduleEvaluator.isAnyActive tells whether the schedules apply now, ScheduleEvaluator.activeUntil returns null when the period does not end within 8 days (for example 24/7 → “no planned end”).

Priority layers

ProfileResolver.resolve builds an ordered list of PolicyLayers, highest priority first:

  1. the running focus session (StrictSession);
  2. the manually activated profile (ManualActivation);
  3. active scheduled profiles, by decreasing priority then increasing id;
  4. the global (default) rules.

A manual profile is not repeated as a scheduled one; disabled profiles are ignored; autoActivation = false means “only activatable by hand”.

Decision algorithm

RuleEngine.evaluate takes the resolved policy, an AppRequest (package, detected zone, usage today, zone usage today) and the system whitelist:

  1. A whitelisted package (SystemWhitelist) is always allowed.
  2. In each layer only the most specific matching rule counts (Zone > App > AllApps); at equal specificity, the most restrictive one.
  3. Layers are walked from top to bottom: Block and Limit are collected, Allow stops the walk (lower layers are ignored).
  4. The strongest collected restriction wins: Block > Limit; between limits, the one closest to being reached.
  5. A reached limit (usage >= limit) blocks until the next local midnight. A limit on a zone is measured against the time spent in that zone (zoneUsageToday); a limit on an app against the app’s time.

The result is a Decision: Decision.Allowed with the remaining time (if limited) or Decision.Blocked with a BlockReason (the highest blocking layer) and the end of the block (the latest end among blocking layers, null if any of them has no known end).

Profiles

  • Order shown = priority (ProfileOrdering): the first one wins when profiles overlap. Moving a profile reassigns spaced priorities (…, 30, 20, 10); a new profile goes last.
  • Editor (ProfileEditViewModel): name, automatic activation, schedules, “block all apps” (then app rules become exceptions), per-app rules Blocked / Limited (5 min → 3 h) / Allowed. Rules that the editor does not display (zones) are kept as they are. Validation by ProfileValidator.
  • Default rules: the same editor without name or schedules, saved with ProfileRepository.replaceGlobalRules (layer 4).
  • Manual activation (ManualActivationPolicy): one at a time, for 1 h, 2 h, until a time, or until turned off. It can be turned off at any time (the firm commitment is the focus session). Activating a disabled profile enables it. An expired activation is ignored by the engine and cleared when returning to the home screen. DeleteProfile also clears the activation of the deleted profile.
